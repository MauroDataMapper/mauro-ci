# Mauro CI

This repository provides shared GitHub Actions workflows and composite actions
for MauroDataMapper repositories. It centralizes common build, test, lint,
publishing, reporting, and notification automation so consuming repositories
can reuse the same CI behavior instead of maintaining copies.

For coding agents integrating these tools into another repository, see
[`AGENTS.md`](AGENTS.md). It can be copied to the consuming repository's root
or supplied as agent context. [`llms.txt`](llms.txt) indexes the documentation,
workflows, and composite actions.

## What this repository contains

### Reusable workflows

Call these from a workflow in another repository using a job-level `uses`.

| Workflow | Purpose |
| --- | --- |
| `gradle-test.yml` | Sets up Java and Gradle, runs a Gradle task, and uploads JUnit results and failure diagnostics. |
| `gradle-publish.yml` | Publishes snapshots from `develop` or Maven Central releases from `main`. Requires signing and repository credentials. |
| `docker-build.yml` | Validates a multi-architecture Docker build without publishing it. |
| `docker-publish.yml` | Publishes the Docker image to Docker Hub on pushes to `main`. Requires Docker Hub credentials. |
| `megalinter.yml` | Prepares shared MegaLinter configuration, runs the configured lint workflow, and uploads reports. The checked-in configurations currently cover Groovy scans in changed-files or full-repository mode. The optional `scan-pr-commits` input enables Gitleaks PR commit-range scanning. |
| `junit-report.yml` | Publishes a JUnit report from the `junit-results` artifact, subject to its event and repository checks. |
| `sarif-upload.yml` | Uploads a MegaLinter SARIF artifact to GitHub code scanning on pushes to `main` or `develop`. |
| `zulip-notify.yml` | Sends a compact Zulip message summarizing build, lint, Docker, and publishing results. Requires `ZULIP_API_KEY`. |

`security-checks.yml`, `verify-actions-lock.yml`, and `security-notify.yml`
support this repository's own workflow validation and security notifications.

### Composite actions

| Action | Purpose |
| --- | --- |
| `actions/setup-gradle-java` | Configures a Temurin JDK and Gradle. Accepts a Java version. |
| `actions/setup-docker-buildx` | Configures QEMU and Docker Buildx for multi-architecture builds. |
| `actions/prepare-megalinter` | Copies the shared MegaLinter configuration into the consuming workspace. Supports the checked-in Groovy changed-files and full-repository configurations. |

The `.github/workflows/actions.lock` file is generated by `gh actions-lock`
and records the external actions used by workflows. Update it with that tool;
do not edit it manually.

## Reuse a workflow

Reusable workflows are called as jobs, not as steps. Replace `<ref>` with a
released version or commit SHA from this repository. Prefer a stable, immutable
reference for production workflows.

For example, a consuming repository can call the Gradle test workflow:

```yaml
name: CI

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    uses: MauroDataMapper/mauro-ci/.github/workflows/gradle-test.yml@<ref>
    with:
      java-version: "17"
      gradle-task: test
```

Inputs and required secrets are declared under each workflow's `workflow_call`
section. For example, `gradle-publish.yml` requires signing and repository
secrets, while `docker-publish.yml` requires Docker Hub credentials. Configure
these in the consuming repository or its GitHub environment, then pass only
the secrets needed by the called workflow.

To use a composite action, call it from a step in a job after checking out the
consuming repository:

```yaml
- uses: MauroDataMapper/mauro-ci/actions/setup-gradle-java@<ref>
  with:
    java-version: "17"
```

## Notifications and reports

The Zulip reusable workflow accepts job results as string inputs. When calling
it to report jobs that may fail or be cancelled, use `if: always()` and pass
their results through `needs`:

```yaml
  notify:
    if: always()
    needs: [test, lint]
    uses: MauroDataMapper/mauro-ci/.github/workflows/zulip-notify.yml@<ref>
    with:
      workflow-name: CI
      build-result: ${{ needs.test.result }}
      lint-result: ${{ needs.lint.result }}
    secrets:
      ZULIP_API_KEY: ${{ secrets.ZULIP_API_KEY }}
```

The JUnit report workflow expects the called test workflow's artifact (by
default, `junit-results`). The SARIF upload workflow expects the
`megalinter-reports` artifact. Call these reporting workflows after the
producer jobs and use `if: always()` when reports should still be processed
after a producer fails.

## Maintaining this repository

Pull requests run `actionlint`, Zizmor, and the action-lock verification.
Keep workflow permissions minimal, pass secrets explicitly, and update the
generated lockfile whenever workflow action references change.
